1.1

What the ledger is for

Money moves in pairs. The ledger stores both halves in one append, and nothing is shown that was not appended.

This manual documents ledger-svc at version 2.4.0, from repository acme/ledger at commit 5b6c792. It follows the service from its one rule down to the rows on disk, and every record shown was captured from a real run NOTES.md §2.

The problem: four kinds of state

A payment touches more than a balance. Before the ledger, each of these lived somewhere different:

Entries — the debit and credit lines, appended in pairs spec §3.

Holds — reserved funds that settle or release exactly once. See the life of one write.

Snapshots — periodic balances so readers never scan the whole log.

Experimental

The README opens with one line of status: “The API changes without notice between releases.” Everything here is true of 2.4.0.

Core rule

“A write atomically appends both entries and any hold change. Only appended state is observable.”

The host drives the ledger, and the ledger appends through one store. The right column of options is omitted. After src/ledger/index.ts.

What this means for you
  • Ask one question of any design: is the balance you show appended? If not, it does not exist yet.
  • Change related things in one write, so a crash can never split them.
  • Never call the network inside a write callback.

1.2

The life of one write

One payment, eight appends, and the order in which a reader can see them.

A write is an atomic append: everything in it is stored together, or nothing is. Here is the smallest program that posts one payment:

Quick start, minimalexamples/00-post.tsTS
const ledger = await Ledger.open(new SqliteStore("ledger.db"));
await ledger.post({
  debit:  "cash",
  credit: "revenue",
  amount: 4200,   // cents
});

Run with npx tsx examples/00-post.ts; the database is created on first open.

Appends 1–3 take the payment from post() to a settled hold. From research/capture/sqlite-commits.txt.

Appends 2–3: settling the hold

The scheduler reserves hold 9 by rewriting it from pending to running, then calls the bank off the line. A crash between the two leaves an open hold that is replayed once on restart running it in production.

Fire and forget

Work started inside the callback and left running can still change the open write, and then fails once it settles. Await every call.

Sources: src/ledger/post.ts; src/holds/scheduler.ts; research/capture/sqlite-commits.txt
